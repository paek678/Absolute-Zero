# 로봇 봇 외형과 등 꼬리 옷장 적용 계획

2026-10-04 기준 상세 구현 계획 v3입니다. 기존 동기화 검토 4건과 재검토 3건(미리보기 결과 전달, 비활성화 후 복구, 교체 도중 실패 복구)을 반영했습니다. 상대 봇은 이번에 받은 로봇 외형을 사용하고, 등 장식 3종과 꼬리 3종은 옷장 선택부터 실제 경기 적용까지 연결합니다. **사용자 승인으로 태스크별 구현·검증을 진행 중입니다.** 현재 실행 상태와 증거는 [검증 원장](../Validation/PLAN_042_results.md)을 기준으로 확인합니다. 아래는 승인된 설계·통과 조건이며, 미실행 검사를 완료했다는 뜻은 아닙니다.

## 적용 범위

- 로컬 봇전의 기본 상대 봇에 로봇 얼굴과 머리카락을 적용합니다. 현재 제공된 로봇 자료가 바꾸지 않는 몸·팔·다리는 기존 그림과 애니메이션을 유지합니다.
- 사람의 등·꼬리는 각각 독립적인 기존 장착 슬롯을 사용합니다. 옷장 미리보기, 착용, 해제, 저장, 재실행, 로비 공개, 경기 입장과 상대 화면까지 연결합니다.
- 사람의 외형 저장값과 봇의 기본 외형을 분리합니다. 사람에게 로봇을 판매하거나 옷장 선택 항목으로 공개하는 기능은 이번 요구에 포함하지 않습니다.
- 봇의 판단·난이도·스탯·아이템 지급·턴 진행은 변경하지 않습니다. 색상 변경, 새로운 팔 그림, 사이드 리깅, 날개·꼬리 전용 흔들림 애니메이션도 범위 밖입니다.

## 현재 확인된 구조와 필요한 보완

| 요구 | 현재 근거 | 보완 방향 |
|---|---|---|
| 봇 기본 외형 | `BotDefinitionSO`에는 5부위 장착 ID만 있고 `DefaultBot.asset`은 모두 빈값 | 장착품과 분리된 선택적 기본 외형 프로필을 봇 정의에 연결 |
| 얼굴 표정 | `Robot_Custom.spriteLib`는 head 15개 상태와 frontHair 2개 상태를 교체 | 기존 포즈에서 로봇 포즈로의 대응표 작성 및 중복 원본 충돌 검사 |
| 머리카락 전체 | Multi 씬은 라이브러리 외에 여러 Renderer의 머리카락 스프라이트도 직접 변경 | 라이브러리만 교체하지 않고 고정 머리카락까지 프로필에 포함 |
| 기존 캐릭터 유지 | 로봇 라이브러리의 팔·몸·하체는 기존 그림을 상속 | 공용 애니메이터·본·아이템 기준점 유지, 외형 그림만 교체 |
| 등·꼬리 장착 | `CosmeticPart`, DTO, 저장, 레지스트리에 Back/Tail 지원 존재 | 새 슬롯이나 통신 규격 없이 각 3종 데이터를 등록 |
| 등·꼬리 표시 | `back_ref_atlas`, `tail_ref_atlas`의 Replacement가 비어 있음 | 실제 잘린 스프라이트, 경로, 위치, 크기, 정렬 순서를 설정 |
| 실제 경기 연결 | `PlayerState`가 서버 승인한 `CosmeticDataNV`를 전달하고 `AZPlayerVisual`이 표시 | 기존 승인·재적용 경로를 재사용하고 새 ID가 끝까지 유지되는지 검사 |
| 미리보기 | 옷장은 카탈로그의 외형별 표시 범위를 모아 카메라 구도를 계산 | 날개·꼬리·모자 조합의 잘림과 과도한 축소 확인 |
| 시각효과 | 추가 레이어는 원본 Renderer의 활성·색·좌우 반전을 따름 | 피해·얼음·고스트·부활 시 새 장식만 남거나 중복되지 않는지 확인 |

사용자 결정은 색상 편집 없이 그림을 교체하고, 기존 5부위 옷장을 활용하는 것입니다. 관련 기록은 `Docs/DESIGN_QUESTIONS.md`의 CU2/CU3 및 `Docs/GAME_DESIGN.md`의 Character Customization 항목입니다. 과거 문서의 Solo 씬·동기화 설명은 현재 `GameScene_Solo`와 내부 NGO 로컬 호스트 구현을 기준으로 해석합니다.

## 구현 구조

### 봇 기본 외형과 장착품의 합성

권장 구성은 데이터 기반 기본 외형 프로필과 기존 장착품 렌더러의 조합입니다.

```text
DefaultBot 설정
  → 시작 시 검증된 Solo 설정에 기본 외형 프로필 보관
  → 현재 세션의 봇 자리 확인
  → 실제 표시 오브젝트 연결
  → 기본 포즈를 로봇 포즈로 교체
  → 봇에게 지정된 5부위 장착품 적용
  → 기존 Animator와 전투 연출 실행
```

- 제안하는 `CharacterAppearanceProfileSO`는 기존 `CosmeticAtlasSO` 형식의 교체 대응을 참조합니다. 런타임에는 읽기 전용으로 사용합니다.
- `BotDefinitionSO`와 `ResolvedSoloSettings`에 선택적 프로필 참조를 전달합니다. 미지정은 기존 외형, 지정된 잘못된 프로필은 작성 검증에서 명확한 오류로 처리합니다. 실행 중 예상하지 못한 누락은 기존 그림과 경고로 안전하게 처리합니다.
- 적용 대상은 `Solo` 모드, `IsBotControlled`, 현재 참가자·세션 세대가 일치하는 자리로 제한합니다. 단순히 1번 자리이거나 호스트 소유라는 이유로 적용하지 않습니다.
- `CosmeticVisualController`는 기존 호출을 유지하면서 기본 외형과 장착품을 한 번에 다시 구성할 수 있는 작은 확장점을 갖습니다. 착용 갱신에서 `Clear()`를 호출해도 로봇 기본 외형이 사라지지 않게 합니다.
- 매 프레임 원래 애니메이션 포즈를 기준으로 교체해야 합니다. 기본 외형과 장착품의 대응표를 먼저 합성한 뒤 원본 포즈에서 최종 그림으로 한 번만 교체합니다. 교체된 결과를 새 원본으로 오인하거나 같은 Renderer에 두 개의 독립적인 후처리가 경쟁하지 않도록 단일 렌더러에서 처리합니다.
- 기존 `CosmeticAtlasRenderer`를 재사용합니다. 새 네트워크 프리팹, 다른 턴 관리자, 전역 이벤트 버스, 봇 전용 전투 애니메이터는 필요하지 않습니다.
- 로봇을 Head 장착품으로 억지 등록하면 모자와 같은 칸을 차지하고 현재 Head의 Overlay 제한과도 충돌합니다. 기본 외형 분리는 이 문제를 피하면서 향후 봇별 외형을 데이터로 바꿀 수 있게 합니다.
- 현재 봇전은 로컬 실행이므로 기본 프로필을 공개 온라인 상태에 추가할 필요가 없습니다. 향후 온라인 봇이 필요하면 프로필 ID 동기화를 별도 설계합니다. 사람의 등·꼬리는 기존 네트워크 장착 ID로 동기화합니다.

### 등과 꼬리

- `back.png`: 작은 흰 날개, 긴 흰 날개, 박쥐형 날개에 해당하는 3개 슬라이스를 각각 등록합니다. 좌우 쌍이 한 슬라이스인지 실제 import 결과를 확인하고, 쌍을 한 벌로 착용하도록 합니다.
- `tail.png`: 곡선형, 털형, 화살촉형 꼬리 3개를 각각 등록합니다. 이름은 임시 표시명으로 사용하며 동물 종류를 새 기획으로 확정하지 않습니다.
- ID 후보는 `back_01`~`back_03`, `tail_01`~`tail_03`입니다. 기존 ID와 중복이 없고 8자 제한을 만족하는지 먼저 확인합니다. 기존 저장 ID를 다른 장식으로 재사용하지 않습니다.
- 항목마다 `CosmeticItemSO`, `CosmeticAtlasSO`, 목록 아이콘, 이름, 부위, 위치·크기·정렬 값을 작성합니다. 기존 `back_ref`·`tail_ref`는 ID 조회와 저장 읽기 호환을 유지합니다. 빈 참조용 항목을 새 목록에서 제외할 경우 표시용 목록 필터만 사용하고 레지스트리에서 삭제하거나 다른 장식으로 바꾸지 않습니다.
- 등은 몸통, 꼬리는 하체 기준점을 우선 사용합니다. pull로 들어온 머리 아래 오브젝트의 좌표를 그대로 복사하지 않습니다. 좌표계가 다르므로 실제 캐릭터 크기와 피벗을 기준으로 맞춥니다.
- 등·꼬리의 뿌리는 몸 뒤에 숨고 끝부분은 실루엣 밖에서 보이게 합니다. 상대 캐릭터와 아이템의 정렬까지 확인하고 일괄 고정값보다 항목별 데이터로 관리합니다.
- 1인칭 화면에는 등·꼬리를 억지로 표시하지 않습니다. 옷장과 다른 사람이 보는 캐릭터에 적용하며, 본인의 팔·아이템 화면을 가리지 않는 것이 정상입니다.

## 태스크 순서와 통과 조건

각 태스크는 구현 후 해당 검증을 수행하고 실패를 수정한 뒤 다음 태스크로 넘어갑니다. 아래 항목은 예정된 검증이며 아직 실행 결과가 아닙니다.

### T01 원본과 적용 대상 확정

- Unity 연결 프로젝트를 확인하고 현재 씬·플레이 상태 및 수정 중인 자산을 기록합니다.
- 실제 사용 중인 원본 캐릭터, Solo 상대 표시, 옷장 미리보기, 1대1·Multi 표시의 Renderer 경로와 라이브러리를 비교합니다. 이름이 같은 여러 player.prefab 중 하나를 임의로 고르지 않습니다.
- 4개 PNG의 import 결과, 투명도, 피벗, 슬라이스 GUID/fileID를 확인합니다.
- 로봇 15개 얼굴 포즈와 앞머리·뒷머리·옆머리의 대응표를 만듭니다. 15개 슬라이스와 라이브러리 15개 라벨이 반드시 일대일은 아니므로 사용하지 않는 그림을 억지로 연결하지 않습니다.
- 동일 Source를 서로 다른 Replacement로 지정하여 마지막 값이 덮어쓰는 충돌, 원본에 없는 포즈, 외곽선 어긋남을 검사합니다.
- `GameScene_Multi`의 `EnemyPlayer_1/body/head`에만 저장된 로봇 라이브러리와 관련 머리카락 교체를 목록화합니다. 로봇 자료는 프로필에 보존하고, 사람 표시의 기본 얼굴·머리카락만 공통 원본과 일치시키는 제한된 씬 수정을 수행합니다. 전체 씬 되돌리기나 위치·카메라·맵 배치 변경은 하지 않습니다.
- 사람이 사용하는 모든 상대 자리의 기본 SpriteLibrary와 얼굴·머리카락 대응이 같은지 확인합니다. 모자 등 이번 대상 외 pull 변경은 별도로 기록하고 보존합니다.
- **통과:** 필수 포즈·고정 머리카락 경로가 모두 결정되고 필요한 원본 파일이 실제 이미지이며 참조가 유효함. 빈 장착 상태의 동일 참가자는 관찰자·자리와 무관하게 같은 기본 외형으로 보임.

### T02 봇 로봇 외형 연결

- 기본 외형 프로필과 로봇 대응 데이터를 만들고 기본 봇 설정에 연결합니다.
- `SoloSettingsResolver`에서 프로필 유효성 검사를 추가하고 확정 설정으로 전달합니다. 관련 작성 검증 도구에도 오류를 표시합니다.
- `AZPlayerVisual`의 표시 연결 완료 전에 현재 봇의 기본 프로필을 선택하고, 장착 데이터보다 먼저 구성합니다. 데이터가 표시 오브젝트보다 먼저 도착한 경우도 처리합니다.
- 씬 연결 해제·재대결 시 적용한 외형 상태를 정리하여 다음 사람 캐릭터에 로봇이 남지 않게 합니다.
- 아래 상세 계약의 검증 후 일괄 적용, 기본 외형 유지, 수명 상태 반영, 적용 결과 보고를 먼저 구현합니다. 현재의 `Clear()` 후 순차 `Add()`만 조합하는 방식은 사용하지 않습니다.
- 미리보기 호출부까지 적용 결과를 전달하고, 일시 비활성화/재활성화와 완전 종료를 구분하며, 교체 도중 실패 복구를 구현합니다. A23~A26은 T02 필수 통과 항목입니다. T04의 화면 검사 이후로 미루지 않습니다.
- **검증:** 미지정 프로필 기존 동작, 로봇 봇만 변경, 사람 꾸미기 보존, 늦은 표시 연결, 장착 재적용, 2라운드·재대결·로비 복귀.
- **통과:** 봇의 대기·공격·방어·마시기·먹기·피해·저온·포옹·얼기/부활에서 원래 얼굴로 깜박이지 않고 기존 행동 판정도 유지됨.

### T03 등과 꼬리 각 3종 등록

- 기존 레지스트리에 새 6종을 연결합니다. 옷장 기존 등·꼬리 탭에 목록·아이콘·표시명을 제공합니다.
- 개별 장식마다 위치·크기·레이어를 실제 캐릭터에서 조정합니다. 에디터 자산 API를 사용하여 .meta와 기존 GUID를 보존합니다.
- 착용·교체·해제와 미리보기 되돌리기를 기존 `ClosetPresenter` / `CosmeticEquipmentService` 흐름으로 처리합니다.
- **검증:** 6종 단독 착용, 등 3종 × 꼬리 3종의 9개 조합, 모자·상의와 병용, 반복 교체에서 중복 오브젝트 없음, 해제 후 원상 복구.
- **통과:** 클릭 가능한 목록과 실제 표시가 일치하고 저장값이 해당 부위에만 반영됨.

### T04 미리보기와 실제 경기 화면 일치

- 대표 모자·상의와 새 6종을 조합하여 옷장과 실제 게임 캐릭터의 위치·크기·정렬을 비교 캡처합니다.
- 날개 폭과 꼬리 끝까지 포함한 카메라 구도를 확인합니다. 현재 고정 구도 원칙을 유지하고 필요할 때 범위 계산의 여백만 조정합니다.
- 해상도별 목록·버튼·미리보기 잘림, 캐릭터 과도 축소, 미리보기 전용 레이어가 일반 카메라에 노출되는지 검사합니다.
- Multi 씬의 기존 비활성 `Customizing_back/tail`과 런타임 레이어가 중복 표시되지 않는지 확인합니다. T01에서 사람 기본 외형과 로봇 프로필을 분리한 결과를 모든 관찰자 화면에서 확인합니다. 원본 예시 오브젝트를 켜서 장착을 구현하지 않으며, 삭제는 참조 확인 없이 수행하지 않습니다.
- **통과:** 옷장과 경기에서 같은 장식으로 보이고 몸·팔·아이템을 부자연스럽게 덮지 않음.

### T05 저장과 서버 승인 및 모드별 검증

- 실제 네트워크 실행 전에 A22의 자산 포함 검사와 동일 빌드 식별 검사를 먼저 수행합니다. T06에서는 마지막 수정 이후 이를 재확인합니다.
- 경로: 옷장 선택 → 로컬 장착 서비스·저장 → 온라인 로비 공개 → 입장 시 소유자의 요청 → 서버 레지스트리·부위 검증 → `CosmeticDataNV` → 각 상대 표시.
- 기존 DTO v1과 5부위를 유지합니다. 새 ID의 길이·중복·부위, 전체 메시지 125 UTF-8 바이트 한계를 검사합니다.
- 저장 후 앱 재실행, 저장 후 바로 경기 입장, 알려지지 않은 ID·잘못된 부위·다른 소유자 요청 거부, 늦은 NV/표시 연결, 재입장·재대결을 확인합니다.
- 로컬 봇전: 사람의 등·꼬리와 상대의 로봇 동시 적용, 봇 기본 외형이 사람 저장값을 읽지 않음.
- 온라인 1대1: 호스트와 클라이언트가 서로의 장착을 동일하게 봄.
- 온라인 3인·4인: 각 자리별 서로 다른 장착 조합, 각 관전자 시점의 일치, 사망·고스트·부활·새 라운드 후 중복/잔류 없음. 필요 시 기존 승인된 Relay 실행 경로와 고정 빌드 경로를 사용합니다.
- **통과:** 같은 장착 ID뿐 아니라 실제 SpriteRenderer 결과와 캡처도 일치함. 수행하지 못한 실제 다중 프로세스 검증은 미완료로 남깁니다.

## 세부 구현 계약

### 데이터와 상태의 소유자

| 정보 | 소유자 | 적용 원칙 |
|---|---|---|
| 실제 장착 ID | 사람은 기존 저장/장착 서비스, 경기에서는 서버의 `CosmeticDataNV` | 표시 코드가 NV나 저장값을 수정하지 않음 |
| 봇 기본 외형 | `BotDefinitionSO`에서 확정한 현재 Solo 실행 설정 | 사람의 장착 저장값을 읽지 않음 |
| 원본 포즈 | 기존 Animator/SpriteResolver | 교체한 로봇 그림을 원본으로 다시 저장하지 않음 |
| 최종 외형 조합 | 표시 오브젝트 하나의 `CosmeticVisualController` | 기본 프로필과 승인된 장착 스냅샷으로 재생성 가능 |
| 사망과 유령 상태 | 기존 PlayerState와 AZPlayerVisual 연출 상태 | 장식이 사망 판정·사망 연출을 다시 시작하지 않음 |
| 로비 공개 결과 | 기존 `LobbySessionWork`의 세션·변경 번호 | 로비 API 지연을 경기 장착 승인 완료로 간주하지 않음 |

상태를 여러 서비스에 복제하지 않습니다. 화면 컨트롤러가 보관하는 값은 서버/시작 설정에서 받은 표시용 스냅샷이며, 새로운 장착의 원본 저장소가 아닙니다.

### 봇 기본 외형 선택

1. 현재 레지스트리의 정확한 `PlayerBinding`과 참가자 식별자를 확인합니다. 같은 자리 번호라도 다른 NetworkObject 또는 다른 세대면 이전 적용 요청을 거부합니다.
2. 현재 모드가 Solo이고 현재 참가자가 Bot일 때만 실행 설정의 기본 프로필을 선택합니다. 사람은 기본 프로필 없음으로 구성합니다.
3. Solo에서는 실행 설정·참가자·매치의 세대가 일치하는지 확인합니다. 원격 온라인 클라이언트는 서버에서만 초기화되는 `MatchCompositionRoot.Generation` 값에 의존하지 않고 기존 `LocalMatchPerspective`의 현재 레지스트리·Binding 검사를 유지합니다.
4. 검증된 기본 프로필을 표시 컨트롤러에 보관한 뒤, 현재 NV에 보관된 장착 데이터를 적용합니다. 새로운 NV 변경 이벤트가 와야만 최초 적용되는 구조로 만들지 않습니다.
5. 사용 중인 프로필의 목록·스칼라 설정은 실행용 읽기 전용 사본으로 고정하고 Sprite 참조만 공유합니다. SO를 런타임에서 수정하지 않습니다. 사용자가 Editor에서 프로필을 수정한 것은 다음 세션에 반영합니다.

### 외형을 갱신하는 한 가지 경로

제안 API 이름은 구현 시 기존 명명 규칙에 맞춰 조정할 수 있지만 아래 책임은 유지합니다.

- `BindCharacter(root, view, baseAppearance)`는 대상과 원본 포즈 기준, 기본 외형을 지정합니다. 기존 사람/FPS 호출은 선택적 인수 기본값으로 동작을 유지합니다.
- `TryApplyEquipment(snapshot, registry)`는 장착만 바꾸고 기본 외형은 유지합니다.
- `ResetEquipment()`는 빈 5부위 DTO를 적용하는 동작입니다. 기본 외형 삭제와 구분합니다.
- `Release()` 또는 기존 `Clear()`의 종료용 경로는 기본 외형·장착·생성 레이어·대상 참조를 모두 해제합니다. 기존 `Clear` 호출자를 전수 확인하여 갱신과 종료를 구분합니다.
- 성공과 실패 모두 `AppearanceApplyReport`로 반환합니다. 성공 여부, 실패 단계, 참가자/표시 대상, 프로필 버전, 정규화된 요청 ID와 실제 적용 ID, 생성 레이어 수, 실패 경로, 이전 구성 복원 여부를 담습니다. 표시용 적용 버전은 로컬 진단 값이며 서버 승인 번호를 대체하지 않습니다. 미리보기는 로컬 표시 식별자를 사용하고 네트워크 Binding을 요구하지 않습니다.

일괄 갱신 순서:

```text
현재 참가자와 표시 대상 확인
  → 입력 데이터 검사
  → 모든 필수 경로와 교체표를 임시 구성에서 확인
  → 새 오버레이를 비활성 상태로 준비
  → 동일 참가자이고 요청이 아직 최신인지 재확인
  → 기존 레이어 비활성화와 새 구성 교체
  → 현재 원본 포즈로 최종 그림 계산
  → Renderer 캐시 갱신
  → 현재 생명 상태와 색·표시 허용 상태 반영
  → 허용된 레이어만 표시
  → 구성·캐시·적용 스냅샷의 커밋 확정
  → 이전 레이어 제거 예약 및 적용 결과 기록
```

- 이 순서는 Unity 메인 스레드에서 프레임을 넘기지 않고 수행합니다. 중간 `yield`, 비동기 완료에 의한 절반 적용, 생성 즉시 기본 활성 노출을 금지합니다.
- 준비 중 실패하면 새 임시 오브젝트를 모두 정리합니다. **동일한 현재 참가자**의 마지막 정상 화면이 있으면 유지합니다. 새 참가자·새 세션에 이전 사람의 장식을 유지하면 안 됩니다.
- 최초 적용 실패는 정상 원본 외형으로 표시하고 명시적인 실패 보고를 남깁니다. 코스메틱 오류 때문에 턴이나 접속 대기를 무한히 유지하지 않습니다. 다만 이 상태로 새 기능 검증을 통과 처리하지 않습니다.
- 같은 프로필·장착·Binding을 반복 적용하면 불필요하게 레이어를 만들지 않습니다. 화면 수명 상태는 중복 적용 여부와 관계없이 다시 맞출 수 있어야 합니다.
- 초기 NV가 빈 문자열인 상태는 장착 미도착입니다. 5부위가 비어 있는 유효한 v1 DTO는 실제 미착용 상태입니다. 두 경우 모두 봇 기본 외형을 지우지 않습니다.
- 정상 승인 이후 비정상·다른 버전 DTO가 들어온 테스트에서는 기존 정상 상태 유지와 실패 진단을 확인합니다. 미리보기·구형 어댑터의 기존 잘못된 버전 거부 동작도 유지합니다.

#### 교체 도중 실패와 커밋 경계

- `CosmeticVisualController`가 갱신 한 건을 소유합니다. 이전 구성의 교체표·원본 포즈 추적·레이어·캐시·적용 스냅샷을 복구 가능한 상태로 보관하고, 커밋 전에는 이전 레이어를 파괴하지 않습니다. 준비 후보는 기존 구성에 등록하지 않습니다.
- 기존 레이어를 숨긴 이후부터 표시 정책 반영까지의 실패도 잡습니다. 새 후보를 즉시 숨기고 기존 구성과 캐시를 복구한 뒤 **현재 포즈·현재 생명 상태**를 반영합니다. 과거 enabled/color를 무조건 복사하여 고스트를 다시 노출하거나 애니메이션을 초기화하지 않습니다.
- 구성·캐시·표시 상태가 모두 일치한 뒤에만 적용 ID/버전을 갱신합니다. 실패한 요청은 중복 적용 방지용 성공 키에 넣지 않아 같은 요청의 재시도가 가능합니다.
- 복구 시 대상이 이미 파괴됐거나 Binding이 바뀌었다면 이전 참가자의 구성을 복원하지 않습니다. 후보/이전 자원을 멱등 정리하고 새 대상의 바인딩 경로에 맡깁니다. 유효한 대상에서도 복구에 실패하면 장식을 숨기고 정상 원본+현재 표시 정책으로 후퇴하며, 복구 실패를 별도로 기록합니다.
- 커밋 뒤 로그·보고 구독자 예외는 표시 실패와 구분합니다. 진단 통지는 교체 구간 밖에서 수행하고, 통지 실패 때문에 정상 커밋을 되돌리거나 같은 후보를 다시 만들지 않습니다. 이전 레이어는 제거 예약 전부터 비활성·캐시 제외 상태이며, 이미 제거된 대상의 반복 정리는 안전해야 합니다.

#### 미리보기까지 결과 전달

- `PrivateCosmeticPreview.Apply`는 DTO 인코딩뿐 아니라 실제 그림 적용과 미리보기 레이어 격리가 성공해야 성공을 반환합니다. 새 레이어의 격리는 화면 노출 전 필수 단계이며 실패하면 위 복구 계약을 적용합니다.
- `ClosetPreviewSurface.Show`는 성공할 때만 `_applied`를 바꿉니다. 요청값과 마지막 성공값을 구분하여 실패한 요청도 다시 시도할 수 있게 하고, 실패를 정상 미리보기로 표시하지 않습니다.
- 장착 후보의 경로/그림 오류는 현재 정상 미리보기를 유지하고 기존 안내 영역에 실패를 표시합니다. 현재의 일괄 `Fail`/`Release` 경로로 정상 화면까지 제거하지 않도록 실패 처리를 분리합니다. 카메라·RenderTexture 등 미리보기 기반 자원이 유효하지 않을 때만 자원을 해제하고 기존 대체 안내를 사용합니다.
- 카탈로그 구도 계산도 동일한 적용 결과를 확인합니다. 새 필수 콘텐츠가 실패하면 정상 항목처럼 범위 계산을 통과시키지 않고 항목 ID와 원인을 보고하며 T03/T04를 실패 처리합니다. 의도된 1인칭 제외와 기존 빈 참고 항목은 기존 호환 정책을 따릅니다.
- 이 변경은 미리보기 표시 계약입니다. 저장이나 서버 승인을 대신하지 않으며, 경기 화면의 실패가 이미 승인된 NV를 되돌리게 하지 않습니다.

### 포즈 교체와 겹침 처리

- 교체 키는 `(view, RendererPath, originalSprite)`입니다. Renderer가 다르면 같은 Sprite를 사용해도 서로 다른 항목입니다.
- 같은 프로필 안에서 동일 키에 서로 다른 최종 그림을 지정하면 오류입니다. 기본 외형과 장착품 간 중복 키는 기존 5부위 순서를 이용해 명시적으로 장착품이 우선하며, 모호한 장착품끼리의 중복은 작성 검사에서 오류로 처리합니다.
- 모든 교체표는 원본 포즈를 키로 사용합니다. `원본 → 로봇 → 장착품`을 실행 중 연쇄 추적하지 않습니다. 이렇게 해야 원본 복구와 동일 프레임 재적용이 결정적입니다.
- 로봇 얼굴의 여러 라벨이 같은 원본을 공유하고 서로 다른 그림이 필요한 경우는 Source 키만으로 표현할 수 없습니다. T01에서 검사하여 해당 경우만 라벨 기반 식별 확장이 필요한지 판단하고, 임의의 마지막 값 선택으로 숨기지 않습니다. 새 그래픽이 필요할 정도의 충돌이면 해당 항목을 중단하고 자료/기획을 확인합니다.
- 몸통을 새 상의 그림으로 교체해도 날개 기준점과 원본 포즈 판정이 유지되어야 합니다. 날개·꼬리의 좌표는 부모의 실제 Transform을 기준으로 설정합니다.
- 현재 `flipX` 복사는 그림만 뒤집고 자식 위치를 자동 반전하지 않습니다. 편측 꼬리에서 Renderer 반전과 부모 음수 스케일의 동작을 각각 확인하고, 필요하면 binding별 위치 반전 옵션을 기본값 꺼짐으로 추가합니다. 모든 기존 모자 위치를 일괄 변경하지 않습니다.
- 정렬 순서는 같은 캐릭터 내 앞뒤뿐 아니라 SortingGroup·다른 캐릭터·아이템과의 관계까지 검사합니다. 동작 중 원본 sortingOrder가 바뀌는 경우에도 지정한 상대 순서를 유지해야 합니다.

### 생존과 사망 표시의 단일 제어

- `AZPlayerVisual`이 현재 표시 정책을 결정하고, 아틀라스는 그 정책과 원본 Renderer의 상태를 함께 따릅니다. 새 아틀라스가 자체적으로 LifeState 이벤트를 구독하여 별도 사망 루프를 만들지 않습니다.
- 생존은 해당 포즈·원본 표시 조건에 따라 노출합니다. 얼어붙는 중에는 기존 죽음 연출이 정한 몸 표시 상태를 유지합니다. 고스트 전환 완료 후에는 몸·등·꼬리를 모두 숨기고 기존 유령 임시 표시만 유지합니다.
- 재구성 뒤 표시 동기화는 `ShowGhostPlaceholder` 등 기존 루틴을 무조건 다시 호출하는 방식이 아니라, 현재 진행 중인 죽음 연출을 보존하는 **부작용 없는 현재 상태 반영**으로 만듭니다.
- 기존 `_spriteRenderers`와 머티리얼 캐시에 새 레이어를 포함합니다. 파괴 대기 중인 이전 레이어는 비활성화하고 캐시에서 제외해 잘못된 부활 재활성화를 막습니다. 반복 적용 중 생성되는 머티리얼 인스턴스가 누적되지 않는지도 검사합니다.
- 사망한 뒤 데이터가 늦게 도착해도 새 레이어는 첫 프레임부터 숨김 상태로 생성합니다. 부활 시 현재 승인된 장착과 기본 프로필을 유지하며 정상 포즈로 복귀합니다.
- 일시 비활성화는 `Suspend`, 동일 대상 재활성화는 `Resume`, Despawn/Destroy/씬 해제는 `Release`로 구분합니다. 기존 표시 소유자가 이를 호출하며 아틀라스에 별도의 LifeState 구독을 추가하지 않습니다.
- `Suspend`는 진행 중 후보 요청을 무효화하고 표시 갱신을 중지합니다. 동일 대상 복구에 필요한 기본 프로필·마지막 정상 구성은 보존합니다. 공유된 PlayerState/레지스트리 구독을 임의로 해제하지 않고, 해당 표시 소유자의 구독을 끊었다면 Resume에서 한 번만 연결합니다.
- `Resume`은 활성 상태와 현재 스폰/Binding을 먼저 검사하고 현재 NV 및 생명 상태를 다시 읽습니다. 비활성화 동안 놓친 변경은 현재 값으로 반영하므로 새 NV 이벤트를 기다리지 않습니다. 같은 대상이면 현재 포즈에서 재적용하고, 다른 대상이면 Release 후 새 바인딩으로 시작합니다. 아직 연결되지 않았으면 기존 초기화 경로로 넘겨 중복 초기화 루프를 만들지 않습니다.
- `Release`는 후보와 정상 구성·기본 프로필·스냅샷·소유한 구독을 모두 정리합니다. OnDisable 뒤 OnNetworkDespawn/OnDestroy가 이어져도 안전해야 합니다. 파괴된 Unity 객체나 종료된 세션을 다시 만지지 않습니다.
- 옷장 미리보기는 기존처럼 닫을 때 자원을 해제해도 됩니다. 다시 열 때 Presenter의 현재 스냅샷을 받아 재생성하며, 이전 창의 요청을 자동 복원해 최신 선택을 덮어쓰지 않습니다. 경기의 Suspend 정책을 미리보기 자원 유지 정책으로 일괄 적용하지 않습니다.

### 서버 승인과 실제 표시 확인

기존 흐름을 유지하며 새 외형 때문에 별도의 네트워크 RPC, 매 프레임 스프라이트 전송, 추가 게임 시작 ACK를 만들지 않습니다.

1. 옷장을 닫을 때 로컬 저장을 먼저 완료하고, 로비 공개는 기존 변경 번호·세션 검사를 통해 진행합니다.
2. 경기 입장 시 소유자의 최신 장착 스냅샷을 제출합니다. 로비 공개가 늦거나 실패해도 예전 로비 DTO로 최신 경기 NV를 덮어쓰지 않습니다.
3. 서버의 기존 소유자·봇 여부·중복 승인·등록 ID·부위·메시지 길이 검사를 유지합니다. 이 기능은 경기 도중 자유로운 장착 변경을 추가하지 않습니다.
4. 모든 관찰자는 서버가 승인한 NV를 기준으로 표시합니다. 자신의 저장 프로필이나 상대 자리의 씬 기본 꾸미기를 상대 장착값 대신 사용하지 않습니다.
5. 네트워크 승인 상태(`Accepted` 등)와 화면 적용 상태를 별도로 기록합니다. 승인 성공 + 필수 경로 누락이면 화면 적용 실패입니다. 테스트는 두 결과를 모두 확인합니다.
6. 새 아이템 ID는 기존 8자 ASCII 제한을 지킵니다. 5부위 최대 길이 ID의 v1 JSON은 정적 계산상 98바이트로 125바이트 제한 이내입니다. 실제 Unity 직렬화 결과는 테스트에서 다시 확인합니다.
7. 테스트 호스트·클라이언트는 같은 코드·카탈로그·그림을 포함한 동일 빌드를 사용합니다. 다른 빌드에 같은 ID가 다른 그림을 가리키는 문제는 NV만으로 해결되지 않습니다. 배포 자산 참조 검사와 테스트 빌드 식별로 방지하며, 구버전 호환 프로토콜 신설은 이번 범위 밖입니다.

## 작성 검증과 오류 처리 상세

`AppearanceBindingValidator`라는 집중 검증 책임을 제안합니다. 새 범용 프레임워크 대신 순수 데이터 검사와 Unity 대상 검사 두 부분으로 나눕니다.

| 검사 | 작성 및 빌드 전 처리 | 실행 중 예상치 못한 실패 |
|---|---|---|
| ID 중복·부위 오류·메시지 초과 | 등록/설정 검사 실패 | 기존 승인 거부, 화면 진단 |
| 필수 Renderer 경로 없음 | 대상 씬·미리보기별 검사 실패 | 새 구성 미적용, 현재 참가자의 정상 상태/원본 유지 |
| 필수 Replacement 없음 | 새 6종 및 로봇 검사 실패 | 필수 항목 미적용으로 보고 |
| Source 없는 Swap | 작성 오류 | 해당 후보 전체 거부 |
| 고정 Overlay의 Source 없음 | 정상 허용 | 현재 생명·표시 정책을 따라 적용 |
| 1인칭에 등·꼬리 binding 없음 | 의도된 제외로 기록 | 실패로 보지 않음 |
| 기존 빈 참조용 아이템 | 명시된 호환 목록에서만 허용 | 이전과 같은 기본 표시, 새 콘텐츠 완료로 세지 않음 |
| 누락된 로봇 필수 포즈 | 로봇 설정 검사 실패 | 기존 포즈 유지하되 실패 기록 |
| 이전 세션/Binding의 완료 요청 | 수명 테스트에서 검사 | 무시하고 후보 정리 |

- 새 엄격한 검사 때문에 기존 빈 참조용 데이터 전체가 갑자기 사용 불가가 되지 않게 합니다. 새 콘텐츠는 엄격 검사, 이전 참고 항목은 명시적 호환 대상으로 구분합니다.
- 데이터가 정상인데 경로만 맞지 않는 문제는 코드 단위 테스트만으로 잡히지 않습니다. 실제 사용 씬과 프리팹 의존성을 열거하여 검사합니다.
- 그림은 AssetDatabase로 매 프레임 찾지 않습니다. 런타임 참조는 직렬화된 프로필/레지스트리에 연결하고 Editor 전용 API는 작성 도구·테스트에만 둡니다.

## 검증 시나리오와 통과 증거

### 구현된 데이터 편집 위치

- 봇 선택: `Assets/Data/Solo/Bots/DefaultBot.asset`의 `Appearance`. 기본값은 `Assets/Data/Cosmetics/AtlasBindings/robot_base.asset`이며, 게임 시작 시 포즈 목록을 복사해 사용합니다.
- 로봇 포즈: `robot_base_atlas.asset`. `Source`는 원래 사람의 포즈 Sprite, `Replacement`는 대응하는 로봇 Sprite입니다. 얼굴 15라벨의 공유 원본을 포함한 변경 포즈 17개와 고정 머리카락 3개를 연결했습니다. 신규 이미지는 만들지 않았습니다.

## 완료 판단과 남은 한계

- 설계 통과 조건은 R1~R7 모두에 소유자·처리 순서·실패 정책·검증 시나리오가 대응하는 것입니다. v3에서 호출부까지의 결과 전달, 중지/재개/종료, 커밋 전후 실패 경계를 보완했습니다. 정적 재검토에서는 이번 지적의 미해결 차단 항목이 없으며, 기획·통신 규격 변경 없이 T01 구현 진입이 가능합니다.
- 구현 통과 조건은 해당 태스크의 필수 검증이 실제 성공하고 관련 신규 오류가 없는 것입니다. 구현하지 않은 기능에 기존 테스트의 성공 기록을 대신 붙이지 않습니다.
- 최종 통과는 A01~A26 중 적용 대상 항목의 증거가 모두 확보된 상태입니다. 환경 때문에 실행하지 못한 항목은 차단 사유와 함께 미완료로 남기며 점수로 대체하지 않습니다.
- 같은 PC의 다중 프로세스 검증은 실제 Relay 경로를 확인하지만 다른 PC·GPU의 화면이나 장시간 플레이 전체를 보장하지는 않습니다. 해당 범위는 별도 잔여 확인으로 기록합니다.
